# Writing a translation unit that still matches

> **Current rules: [decisions.md](../decisions.md).** That page lists the design decisions and compromises in force
> (representation, linkage, data layout, flags, blobs), each with its status. This page is the history and the
> detailed evidence behind them; prefer decisions.md when the two differ.

Every original translation unit (TU) is one source file under `src/game/` (see [architecture.md](../architecture.md));
the merge wave that turned the per-function files into these files is complete. This page is the reference for editing
such a file without breaking the match: the generated static initializer, every mismatch cause met with the fix that
worked, representation decisions for shared types, the path-hash quirk, inline/linkonce functions, how data is defined
and laid out, and linkage. Read "Path-hash quirk" first, then "Mismatch causes and fixes", then "Recurring asm idioms"
before renaming any helper. The per-TU merge log is in git history (`git show 3493d772:docs/guides/tu-merging.md`).

## Rules

- One file per TU, functions in address order (the original source order). `.c` only if a function cannot match as
  C++ (none so far). `config/matched.csv`'s `source` column names the file of every function.
- A function whose current symbol is a plain name is defined `extern "C"`; a function whose symbol is mangled is defined
  with the C++ signature that mangles to it. Renaming is tools/rename.py's job ([naming-workflow.md](naming-workflow.md)).
  Declare callees with the linkage of their current definition (plain-named callees `extern "C"`); relocations are
  masked, so callee spelling never changes the match, but it keeps the native link honest.
- Types: a type used by more than one TU goes to `include/sly2/` (header changes in their own commits). TU-private types
  stay in the `.cpp`.
- Add layout asserts (`typedef char assert_X_size[sizeof(X) == N ? 1 : -1];`) for sizes the match or the data proves.
- Check with `python3 tools/matchtool.py check <tu>.cpp`: every function prints MATCH, no function of the TU is missing
  from the object, no extra symbol with an address shows up, and every data symbol the file defines MATCHes ("Data").

## Procedure

The file of a TU starts with its header comment and the aliases for the generated functions:

```cpp
// <tu>.cpp -- <what it is>. TU 0xSTART..0xEND (<n> functions, address order).
// SLY2_ALIAS: __static_initialization_and_destruction_0=StaticInit_<tu>
// SLY2_ALIAS: _GLOBAL_$I$*=<current name of the stub>
#include "sly2/slotheap.h"
...other includes...

// 0xADDR StaticInit_<tu> and its _GLOBAL_$I$ stub: generated by g++ for the six engine slot pools.
SLY2_INSTANTIATE_SLOT_POOLS()
```

Put `SLY2_INSTANTIATE_SLOT_POOLS()` directly after the includes (see "Pool order" for why). A TU may also emit
out-of-line inline/template instances that live in the linkonce area at the end of `.text` (0x254F00..); see "Inline
functions and linkonce copies". m2c-style bodies (`M2C_FIELD`, the C-only m2c prelude) do not belong in a TU file:
rewrite them as readable C++ against the shared types.

## The generated static initializer (StaticInit_<tu> and _GLOBAL_$I$)

Almost every game TU ends with a 77-instruction `StaticInit_<tu>` (g++'s `__static_initialization_and_destruction_0`)
and an 8-instruction `_GLOBAL_$I$...` stub that calls it with `(1, 0xFFFF)`. They are not user code: g++ 2.95 emits
them for six template static slot pools that every TU instantiates, each guarded by a sentry
(`if (++sentry == 1) InitSlotheap(&pool, cb, c, 16)`). `include/sly2/slotheap.h` reproduces them with
`CSlotPool<CB, C>::s_pool` and the `SLY2_INSTANTIATE_SLOT_POOLS()` macro (from the cleanup pilot).

The object names of these two functions cannot be bound through `config/symbol_addrs.txt`:
`__static_initialization_and_destruction_0` is the same in every object, and the stub is named after the source file
(`_GLOBAL_$I$src_game_platform_memory_slotheap.cppQJeaaa`). The `// SLY2_ALIAS: obj=config` lines in the first 4000
bytes of the file rename them before comparison (matchtool and progress.py; a trailing `*` matches any suffix).
Alias them to the names config already has (`StaticInit_<tu>` and the stub's current name, usually `func_XXXXXXXX`).

TUs whose static initializer is not the standard 77 instructions have statics of their own. Read the target: if it
is the six pool blocks followed by more blocks of the same shape (`if (++sentry == 1) InitSlotheap(&obj, cb, c, 16)`),
the extra objects are template statics too. spliceutils (133 instructions) has five more slot heaps, 0x18 apart
(0x452188..0x4521E8); a TU-private `template <int CB, int C> struct CSpliceHeap { SLOTHEAP slotheap; ctor; static
CSpliceHeap s_heap; }` with five explicit instantiations after `SLY2_INSTANTIATE_SLOT_POOLS()` matched, and the code
that used the raw `D_004521xx` addresses now names `CSpliceHeap<CB, C>::s_heap`. Other shapes (`tu_1147D8` 185,
`tu_114AE0` 1926, sprbuf's SPRBUF array with a dynamic initializer) need their own spelling; not done in wave 1.

Wave 5 spelled the three of them as the file-scope objects they are, defined before `SLY2_INSTANTIATE_SLOT_POOLS()`
in their original order, so g++ generates the initializer:

- tu_1147D8 and tu_114AE0 contain no code of their own: `RGBA D_0029A7C0[16] = { RGBA(0, 0, 0, 0xF), ... };`
  (256 entries in tu_114AE0) with a private four-byte `RGBA` constructor, then `CLUT D_002DD500(D_0027A778);` and
  `BMP D_002DD520(D_0029A790);` whose inline constructors call func_001EAD98 / func_001EB050 (CopyClutHeader /
  CopyBmpHeader) on a header in .data. The natural array initializer matches; the per-function tu_114AE0 needed a
  dead countdown to steer cse, which g++'s own array-init code provides.
- sprbuf: `SPRBUF D_003DD2C0[2] = { MakeFirst(), MakeSecond() };` (SPRBUF's constructor memsets it), then the pools.
  With SLY2_ALIAS binding the initializer, the asm-label hack and its `SLY2_ASM: gnu-reorder-db` line go away and
  the merged file builds and matches with the default toolchain (all five functions); it no longer needs GNU as.
  Merged at the end of wave 5.

### Globals with destructors

A StaticInit whose `else` branch (initp == 0) calls destructors, and a third stub `_GLOBAL_$D$...` that calls it with
`(0, 0xFFFF)`, means the TU defines global objects with a constructor and a destructor. Five TUs had them: cm (g_cm),
sw (g_sw and a four-word table header), memcard (two dialog widgets), screen (nine screens) and sound (g_sndmgr).
What matched in all five: define each object in the merged file, in the original order and before
`SLY2_INSTANTIATE_SLOT_POOLS()`, as a view of its bytes whose inline constructor calls the C-named constructor and
whose inline destructor calls the linkonce destructor with g++'s in-charge flag (`~CMG() { func_00258290(this, 2); }`);
g++ then emits the destruction in reverse order itself. Add `// SLY2_ALIAS: _GLOBAL_$D$*=<stub>` next to the other two
aliases. Several objects of one shape: a small template over the size (screen's `SCRINL<CB>` / `SCRCTOR<CB>`); an
inline constructor taking a selector folds after inlining (memcard). When the destruction first releases member
pointers and then calls the base destructor (sound: three counted pointers, one an array of eight, then ~BASIC), make
the base destructor a base class's and the pointers members with inline destructors, and give the derived class an
explicit empty inline destructor (the implicit one was emitted out of line as `_$_7SNDMGRG` and called); g++'s own
array destruction is the `if (pa) { e = pa + 8; while (pa != e) Release(--e); }` loop of the target.

### Pool order

Naming a pool in code (for example a class-specific `operator delete` that frees into
`CSlotPool<0x18, 0x800>::s_pool`) instantiates that pool at that point. If the explicit instantiation comes later,
the pool's init block moves to the front of `StaticInit_<tu>`: varb showed a 4-instruction diff (two `li` pairs
swapped). Instantiating all six right after the includes keeps the order.

### The pools are real allocators

The pool objects at 0x4520A8 + 0x28*i are what Splice nodes are freed into: `CPair::operator delete` frees into pool
0 (`CSlotPool<0x14, 0x2000>`, slot size 0x14 == sizeof(CPair)) and `CVarb::operator delete` into pool 1
(`CSlotPool<0x18, 0x800>`, 0x18 == sizeof(CVarb)). Spell such uses as `&CSlotPool<CB, C>::s_pool.slotheap`, not as the
raw `D_004520A8`. The other four are the frames (0x28/0x200), procs (0x1C/0x800), sidebags (0xC/0xC8) and methods
(0x14/0x100): CONFIRMED by the GC pool templates (sly2/gc.h `CGcPool<T>`, link/linkonce-pools), whose instances for
those kinds free into them.

Other observations:
- `.c` files compiled as C++ matched unchanged in every other case (about 20 files): expect B4 only for by-value
  structs that are passed on, and the `!`/bool difference above.
- Six linkonce helpers carried `// SLY2_CC:`/`// SLY2_CFLAGS: -O2 -G0` overrides in their own files; in the merged
  `.cpp` they match with the default C++ flags, so the overrides were not needed (spliceutils). Check this rather than
  copying overrides into a merged file (a file-level override would apply to every function of the TU).
- Per-function gcse stand-ins (brx_sw's dead `if (fNever)` block that sizes the gcse hash table) survive the merge:
  that table size is per function, not per file.
- When rewriting doc links, match `\.(cpp|c)` in that order: `(c|cpp)` stops at `.c` and leaves `pp` behind (fixed
  in a follow-up commit of wave 1). Run `python3 -I tools/linkcheck.py` after each merge.
- Not hit yet: inline methods or class definitions that become visible in the merged TU and change a function's
  codegen (pilot blocker B6). The gifs/vifs cases suspected of it were draft-body and register-pin differences
  (wave 3, see "TUs with an older multi-function file").
- Wave 2 (asm-free TUs up to 21 functions, plus three small asm TUs): of about 110 per-function files, the only
  C-vs-C++ codegen differences were the rows above (draw, barrier, find, rumble, bas); everything else matched on the
  first compile once types were unified. Most of the work is unifying the per-file views of one object into one type.
- `.c` callers that passed a hidden result pointer by hand (`GetSpeakerSubtitleColor(&c, k)`, `GetGlobalSaveVar(&ref,
  ...)`) become by-value calls in C++ and match: g++ uses the same hidden-pointer convention for a returned non-POD
  class (tu_2275B8, difficulty).
- Defining a class's first virtual function in the merged file makes it the class's key TU: g++ then also emits
  out-of-line copies of the class's inline members (bq: `__17CQueueInputMemoryPUci`) and, with RTTI, `__tf...`
  typeinfo functions. They have no address in the binary (the code exists nowhere there) and show as extras, not
  mismatches. Since C++ is compiled with `-fno-rtti` (build/rtti-palettes, as the game was) the `__tf` ones are gone;
  the constructor copy stays.
- A per-function `.c` that defines a mangled name as a C symbol (`InitDl__FP2DLi`, `FindSwObject__FP2SWi3OIDP2LO`)
  becomes the C++ function that mangles to it; its parameter types must then carry the exact names (`SW`, `OID`,
  `LO`, `CID`), so a TU-private view of LO is called `LO` (find). The same applies to callee declarations: a callee
  whose symbol is plain must be declared `extern "C"`, and one whose symbol is mangled must be declared with the types
  it names; a literal-mangled name declared outside `extern "C"` (`CRef EvalExpression__FP5CPairP6CFrame(...)`) gets mangled
  twice. Wave 2 fixed three such slips in a follow-up commit; check every prototype against config/functions.csv.

  arguments) stays a C-linkage function under that symbol until it is renamed.

## Representation decisions

The four "hard" TUs (dzg, jthands, spliceobj, sensor) had functions carrying competing private views of the same
structs. The rules applied (from the project lead): separate structs where views genuinely conflict, no speculative
unions (a union only where a kind/mode field selects what the bytes hold and the code shows it); extended structs
become derived structs so matched code keeps the base unchanged; the most informative typed pointer, never `void *`
plus casts; small documented matching-only islands (comment "this form exists to reproduce the original codegen").

### Vtables emitted (data/vtables)

The registry classes' vtables (slice 2 made the classes real, but nothing emitted their vtables) come from their key
TUs now, as the original build made them: 174 vtables (65,040 bytes; 10 of them the grab-spot classes' secondary
`_vt$<CLASS>$8GRABSPOT` tables, emitted with their primary) in 81 TUs, each MATCHing the ELF slot for slot. Every
touched file keeps all functions and data MATCHing; nm symbol sets change only by the new `_vt$` definitions and the
slot functions they reference (all config names); symcheck is identical to the branch start (35 unresolved, 0
duplicate strong globals: the vtables are weak `.gnu.linkonce.d` definitions); relverify 37,168 relocations OK, 0
mismatched.

**The mechanism.** g++ 2.95 emits a class's vtable (in `.gnu.linkonce.d._vt$...`) in the TU that defines the class's
key function, its first declared non-inline, non-pure virtual. For each class: the key TU is the TU whose place in TU
order matches the vtable's place in the ELF's linkonce area (the area is in TU order; where a class's own virtuals
are defined in several TUs the order decides: HND is hnd.cpp's, not grabspot's, because GRABSPOT's own vtable
(0x2D28D8, grabspot's) lies between; JT jt.cpp's, SO so.cpp's, XFM xform.cpp's: both candidates fit, the one with the
class's functions was taken). In that TU one virtual whose function the TU defines as a C-named function becomes the
member definition, and its declaration moves to the front of the class (sly2/classes.h or the class's header):

```cpp
// was: extern "C" void InitContessa(GUARD *pguard) { InitStepguard(pguard); pguard->n4A4 = 1; }
void CONTESSA::Init()                     // header: virtual void Init() __asm__("InitContessa"); declared first
{
      GUARDV *pguard = (GUARDV *)this;    // the TU's view, renamed (see below)
      InitStepguard(pguard);
      pguard->n4A4 = 1;
}
```

The member's asm label is the function's own symbol, the body is unchanged, and the view pointer is a cast of `this`:
no conversion changed code. Further parameters keep their names (`MSGID msgid_m` and `int msgid = (int)msgid_m;` where
the view's type differs). A function in a per-function namespace is moved out of it and opens it
(`using namespace M_x; M_x::S *p = (M_x::S *)this;`), with using-declarations for the names the namespace shares with
the file scope (`using M_x::D_003DD490;`) and a qualified call where a class member hides a free function
(shape.cpp: `M_func_001E9AC0::Add`, hidden by LO::Add). Shortest bodies at file scope were taken first.

## Path-hash quirk (asm functions)

GCC 2.95 hashes the source file name and the line number into the gcse ordering of inline-asm expressions; in rare
functions that ordering decides stack-slot numbering, so the match depends on (sum of path bytes, line) mod 287.
A merge changes both the path and the line of every function. If a merged function that contains inline asm misses
only by a few stack offsets, pin the name with `#line N "<repo-relative path>"` and keep the asm helper in the line
window that matches (example: func_001D3450 in `src/game/gameplay/objects/tu_1D1370.cpp`, namespace M_func_001D3450).

What wave 2 measured (on func_001D3450, by changing only its `#line 13 "<path>"` pin; MATCH unless noted):

| pin | result |
|---|---|
| original | MATCH |
| same path with two digits swapped (same byte sum) | MATCH |
| same path with one digit +5 (byte sum +5) | MATCH |
| line 23 (+10) | MATCH |
| line 53 (+40) | 64/637 instructions differ |
| `"a.cpp"`, line 13 | 5/637 differ |

So the input is (byte sum of the presumed file name, line of the asm text), with a window of roughly 30 lines; the
name that counts is the one `#line` sets, not the real file. The line is that of the asm statement itself, i.e. of the
inline helper that contains it (VU_FLOAT at line 57 there), not of the function that uses it.

Recipe for merging a sensitive function: directly before the asm helper's definition in the merged file write
`#line <line the helper had in the per-function file> "<per-function file's pinned path>"` (func_001D3450: `#line 57
"src/game/gameplay/objects/tu_1D1370/func_001D3450.cpp"` before `struct VU_FLOAT`), and directly after it
`#line <real next line> "<merged path>"` so diagnostics point at the merged file again. That reproduces (sum, line)
for the asm exactly, wherever the helper ends up in the merged file.
A cheaper equivalent is any (name, line) pair whose sum lands in the same window, but the verbatim pin is easier to
review. Helpers shared by several functions of the TU are defined once, so a sensitive function constrains where that
shared helper sits.

In practice it is rare: the three asm TUs of wave 2 (sjis: register-pinned `addu`/`sll` helpers; sky: a `pextuw`
helper; tu_1603B8: VU0 macro-mode asm with `"j"` operands) merged with no pin, and UpdateSky and ApplyXfmConstraint
still matched under eight different `#line` pins each. Only functions where gcse PRE creates pseudos from an asm (and
those pseudos then get stack slots) are sensitive. tu_1D1370 (44 functions), which holds the one known case, was
merged in wave 9: its namespace keeps the per-function file's verbatim `#line 13 "src/game/gameplay/objects/tu_1D1370/
func_001D3450.cpp"` (the string only names the presumed file; the directory is gone) and a `#line <next line>
"src/game/gameplay/objects/tu_1D1370.cpp"` after the namespace restores the merged name. func_001D3450 and every
function after it matched.

## Linkonce instances

Some TU directories also hold a small function from the linkonce area (0x254F00..0x259DE4): an out-of-line copy of an
inline member or template, homed in the TU that first uses it (formerly proc 0x257038, varb 0x257430: counted-pointer stores, now
`CRefPtr<T>::Attach` instances, "The Splice GC pool family" below).
Keep it in the merged file, after the TU's own functions, as a plain C-linkage function under its current symbol,
with a comment. Turning it back into the inline member it was would also need the callers to stop inlining it, which
is a separate step. For linkonce copies that no code calls, see the next section.

## Inline functions and linkonce copies

(Inline pass 1.) A function defined in a header (inline, in-class member, template) is compiled into every TU that
needs an out-of-line copy of it, in its own section `.gnu.linkonce.t.<symbol>` with a weak symbol; the linker keeps one
copy and puts it in the linkonce area 0x254F00..0x259DE4. So the way to "home" such a copy is to define the function in
its header and make one TU need it. tools/matchtool.py and tools/progress.py find it there with no change: they compare
every FUNC symbol of the object by name (weak and linkonce ones included; each symbol is read from its own section).

What makes g++ 2.95 emit the copy (all measured with matchtool on a scratch file):

- Taking its address in any TU (or a call that is not inlined) emits a free inline function, and an inline member of a
  class without virtual functions, in that TU.
- An inline member of a polymorphic class is NOT emitted there: the TU only references it as an undefined symbol.
  g++ emits the inline members of such a class only in the class's key TU (the one that defines its first non-inline
  virtual function, where the vtable goes; compare bq's key-TU extras above), and only those that TU needs. No TU of
  ours defines LO's, SO's, STEPPLAYER's... key function, so the member form cannot produce the copy.
- Unused inline functions in a header emit nothing: after the pilot all 163 sources that include `sly2/` headers
  were rebuilt; every function still matched and no addressed symbol appeared in another object.

The 56 functions that were in src/game/core/linkonce/unhomed (removed in pass 3) were all of one kind: no code refers to them; the only references
are pointers to member functions (`{0xFFFF0000, pfn}`: delta 0, index -1, non-virtual) in the option table g_aeopid
(D_002AC880, 0x28-byte EOPID records: get PMF at +0x8, set at +0x10, setUser at +0x18, ensure at +0x20). The owner class
of a record is the root-most class whose option array in g_mpcidarysplopt (D_00279AD0, 199 x {count, SPLOPT *}) lists
it. g_aeopid lives in crt0_splicewrap's .data and was not in the source (it is since data/crt0-tables: "The
crt0_splicewrap tables" below; its records reference these accessors through asm labels that do not emit them), so:

### The Splice GC pool family

## Data

`matchtool.py check` also verifies every data symbol a file DEFINES whose address is known (a `D_XXXXXXXX` name, or a
`name = 0xADDR; // type:data size:0xN` line in config/symbol_addrs.txt): initialized data byte for byte against the
ELF with relocated words masked, .bss by placement (and size, when symbol_addrs.txt gives one). It prints one line per
data symbol after the functions: `D_002C0D00 @0x2C0D00 [.data 0x4]: MATCH`, or the differing words
(`!! <addr>  <target bytes> | <ours>`), or a placement problem (`ours is zero-initialized (bss), target is in .rodata`).
Extern declarations are not checked; a symbol with no known address (template statics, `g_eopidref_*`) is skipped.

Defining a TU's data:

1. Find what the TU owns. Data is linked in TU order like code, so the TU's .data/.bss is the range between the previous and the next TU's data; a word inside that range
   that no code names (pipe's D_002C0D04) is the TU's too.
2. Replace the TU's `extern` declarations by definitions with the values read from the ELF, in address order (g++
   emits .data and .bss in definition order; memory's object reproduced the target's .bss offsets exactly). Use the
   type the code reads and the layout shows: a 16-byte stride of three floats is a CLQ (water), the gap to the next
   TU's data sizes an array (memory's `D_002F63A0[50]`). Keep the constness the section shows (.data = non-const;
   .rodata = const or a literal). Do not claim padding-looking zeros up to the next TU's data (hnd, sensor).
3. Leave `extern` declarations in other TUs' files as they are (memcard still declares memory's globals).
4. `python3 tools/matchtool.py check <tu>.cpp`: every function still MATCH (defining a global in the TU that uses it
   can change code generation) and every data symbol MATCH. Commit per TU: `data: define <tu>'s ... in <tu>.cpp`;
   config/matched.csv does not change.

Known limits: the ELF has no symbol table, so a definition that is too short passes unless symbol_addrs.txt gives
`size:`; relocated words are masked, so a wrong pointer in a table still passes; unnamed literals and strings are not
checked (only named symbols). Our compiler puts a const object with a dynamic initializer in .bss, where the original
has it zero-filled in .rodata: tu_1147D8's and tu_114AE0's palettes `D_0029A7C0` / `D_002A2900` carry
`__attribute__((section(".rodata")))` for it (see "Resolved decisions" under Data). The vtables are linkonce data at the end of .data (0x2C8940..0x2DD230), not owned
by any TU. The end of .bss from 0x4421A0 was taken for commons (phase 3); it is in TU order up to 0x452098 and is
defined by layout since phase 7 ("Phase 7: .bss and data gaps"); only the class and template statics after it and
in `.sbss` are commons.

Rules found while defining the data of every TU (the early data survey's owner guesses were often wrong; layout wins):

- **What to leave out.** `.bss` addresses inside g_sw (0x3DD490..0x3E1C20) are SW fields, not objects (ms's "first
  glob owner", the slot heaps of tu_1709A8/tu_20B840/noise/frm, light's lists). End of `.bss` from 0x4421A0 (in TU order after
  all: phase 7), the splice pool words in `.sbss`/0x4520xx and the `.bss` around 0x3DD0E4..0x3DD190 (cd, menu entries between sound and
  sprbuf) are not in TU order: not defined. Also left: vtables, class rows, engine tables, PMF constants (literal
  phase), records and tables holding function pointers (pointer phase: cheat's CODEs, menu's items, tu_15CD68's label
  tables, draw's pass hooks), the shared constant block 0x2A2D00..0x2A2E10 (identity matrices, unit/zero vectors right
  after tu_114AE0's palette; owner undecided) and the two zero-filled palettes (since resolved: section attribute, "Resolved decisions" below).
- **Ownership by layout beats the survey's first-user guess** where they disagree: frm owns D_002DEA4C (survey: font),
  cd owns D_002BD4C0 (survey: tu_14A008, medium), phasemem owns the RPL buffer D_003B3980 that only other TUs name;
  basic's two int tables lie in crt0_splicewrap's `.rodata` (0x27A108.., generated area) and are not basic's
  (defined in class_registry_options.inc since data/crt0-tables).
- **Spelling.** `.data`: a plain definition. `.rodata`: `extern const T x = v;` (`extern` keeps the symbol, `const`
  puts it in `.rodata`); strings as `extern const char x[] = "...";`. Where a callee or return wants `char *`, change a
  plain-C-symbol callee's parameter to `const` (check the declaration is inside `extern "C"`) or cast; never change a
  mangled callee's parameter types (IsWithinLimits__FP2LMf, CdPath__FPcT0i: the symbol would change). A zero-filled `.rodata`
  row that the code uses as a string is `""` (tu_11AFE0, tu_1BAB50, brx). `= 0` keeps a zero word in `.data`.
- **Sizes.** Arrays are 8-byte aligned on the EE, so zero words before an 8-aligned next object are padding: size an
  array by the count the code uses (loot tables 9, logo triangles 53/22/11/11/62, snip tables by the BindLoOidTable
  count), not by the gap. Two names into one array (tu_1471C0's D_002BD398/D_002BD39C) stay extern; so do records whose
  view type overlaps the next datum (gs' 0xF0-byte DRAWENV view).
- **16-byte vectors read as qwords** cannot be initialized through a qword-first type: use a TU-local
  `union VQ { float af[4]; qword q; };` and `.q` at the reads, or list the floats first in an existing union U (no layout
  change; cane, hurt, grab, tu_1B9F80).
- **When a visible value changes code.** A const definition lets g++ fold the value: cd's UpdateCd stopped matching.
  Declare the objects `extern const` above and define them at the END of the file (gcc 2.95 compiles function by
  function, so a later definition is not seen). If the const qualification alone changes the code (tu_185130's
  D_002A5688), leave the extern. `extern const` declarations of `.data` words that comments describe as code-generation
  devices (path D_002C0C04, tu_185130 D_002BE918) stay extern too.
- **Namespace-mangled externs.** In files with per-function namespaces, an `extern` inside a namespace without
  `extern "C"` refers to `_<n>M_<view>$D_...`, which no native link resolves (relocations are masked, so the match never
  showed it). A definition there must carry `extern "C"` (`extern "C" T x = v;`, `extern "C" { T x; }` for `.bss`); the
  data check silently skips mangled names, so list the object's data symbols after each TU. Fixed for the data defined
  here (step, hurt, grab, jt, tu_1D1370, glob). The remaining references (555 data, 47 functions in 28 files, waves
  9/10 and the big six included) were fixed on integrate/round2: see "Linkage of namespace-scoped declarations" below.
- **Order.** Definitions go in address order where the declarations allow; in the big per-function-view files (tn,
  jt, tu_1D1370, glob) they sit at their first declaration, so the object's data order follows the declarations (each
  symbol still MATCHes; the layout is not reproduced).
- **Values** come from the ELF: floats as the shortest literal that round-trips (FLT_MAX as `3.40282347e+38f`), words
  that the code reads as float bits stay ints with a comment.
- **End-of-file block.** In the big per-function-namespace files the TU's data goes in one block at the END of the
  file, at file scope, in address order (`// ---- Data owned by this TU, in address order ...`). No function sees a
  definition, so nothing folds (no define-after-use juggling), and the namespaced `extern "C"` declarations above,
  whatever type each view gives the object, refer to the same symbol: g++ 2.95 does not compare an `extern "C"`
  declaration in one namespace with a definition in another (tested). A file-scope declaration must agree with the
  definition: make it `extern const` for `.rodata` (no code change anywhere; a `char *` return or argument then gets
  a cast, e.g. `return (char *)D_002A75E0;`, `load_file_from_disc(..., (char *)D_002A6CA0)`).
- **Types.** Use the type the code gives where it is a plain or header type: `LM`, `CLQ` (`{{{g0, g1, g2, 0}}}`),
  `SMP`/`SMPA` (SmoothValue/PosSmooth parameters, also when the code passes `char[]`), `VECTOR4` for a 16-byte vector,
  `SNIP` records for BindLoOidTable tables (count from the call). A float pair or float followed by zero words up to
  a 16-aligned object leaves the padding unclaimed; a POLY between two such pairs is a CLQ (it must be 16-aligned).
- **Under C linkage in a namespace.** Three cases need a type the file scope cannot give: an object declared `qword`
  at file scope (no float initializer: rip's D_002C1F40/F90/FA0, tn's D_002C41C0 and VECTOR4[5] D_002C4290), a type
  with no aggregate initializer (CLASSDESC derives from CLASSINFO), and a view-local type (screen's ITEM[14], relay's
  CMD, memcard's ENT[], game's 0x1C-byte g_game). Define it as `namespace M_x { extern "C" { T D_xxx = ...; } }`,
  reopening the view's own namespace when its type is wanted. Same symbol, no change to the reads.
- **Pointer tables.** Pointees are declared with asm labels in a namespace of the data block
  (`void StartupDma() __asm__("StartupDma__Fv");`), so no existing declaration changes; casts to the element type.
  The data check masks relocated words, so each table was also checked with a scratch resolver (R_MIPS_32 symbol +
  addend against symbol_addrs/functions.csv, compared with the ELF word): class table 383, builtin table 169,
  render-pass hooks 24, startup stages 19 pointers, all correct.
- **Is it an object or a field?** Before defining a `.bss` name, look at its neighbours and their owners in text
  order. Found this phase: D_002E0C20 (game), D_002E0CB4 (cheat), D_002E0CBC (joy, defined in phase 1 and now back to
  `extern`) and D_002E0CCC (sw) are fields of g_joy (JOY, 0x1100 bytes from 0x2DFC00); D_002DDED4..D_002DDF18 are
  g_clock fields; D_002DEB40/44/48 g_game fields; D_002E5270 is an address inside memcard's thread stack. A scalar
  declared by the code with much more room to the next name than its size stays extern ("extent unclear").
- **Ownership by text order** again beat the survey: g_joy, g_grfjoyt, g_grfusr (survey: guardbhv) are joy's; the
  ship singleton D_002DFB80 (guardbhv) is tu_17F090's; g_clock (cd) is clock's; the builtin table D_002BBB90 (no
  owner) is bif's, right after bif's D_002BBB70 (eval only indexes it). `.rodata` names the code no longer uses (now
  literals in the function) are not defined (guardbhv's D_002A5588..D_002A55A0).
- **PMF constants** can look like 64-bit integers: tu_17F090's D_002A5630 `{0, 0x53, 12}` is a virtual
  pointer-to-member (delta 0, vtable index 0x53, vptr at +0xC) passed to PostSwCallback; left for the literal phase.
- **Vtables.** g++ 2.95 emits a vtable (`_vt$<class>`, `.gnu.linkonce.d`) only where the class's virtual functions
  are real members. Six are: CLinearHeap (heap), CBinaryInputStream (bis), CQueueInputFile and CQueueInputMemory

  makes the data check compare them with the block at the end of `.data`: all MATCH. The word after the first entry
  (the typeinfo slot) was relocated to a `__tf*` function in our objects (so the data check, which masks relocated
  words, hid it) and is 0 in the game: the game was built without RTTI, and C++ now compiles with `-fno-rtti`
  (resolved, below), so the slot is an unrelocated 0 compared byte for byte. The other 238 cannot be emitted yet:
  the classes' virtual functions are free functions with C names (the LO/BASIC hierarchy, CSwHeap, CMemInputStream,
  ...; heap.cpp's comment), so the classes are views. Four objects emit vtables of view classes (SM, ACCMISS, JT,

  vtable has no counterpart in the game (the block holds one `{EndPrim__4DMASi}` vtable, DMAS's). Matched code that
  names a view's vtable (`_vt$Q23REG2SO`) is resolved by config/link_aliases.txt instead (see "Linkage of

Resolved decisions (user, build/rtti-palettes):

- **`-fno-rtti`** is in the C++ build flags (matchtool's CFLAGS, which progress.py and tools/link.py use; stripped for
  `.c`; per-file `SLY2_CFLAGS:` headers state their whole flag list and are unchanged, and the two `.cpp` ones,
  libgcc's `__main` and 989snd's `snd_SendCurrentBatch`, define no classes). Evidence: every vtable in the ELF has 0
  in the typeinfo slot, and no `__tf*`/`__rtti_*` code exists in it; no source uses `typeid`/`dynamic_cast`. The
  six vtables are byte-identical, the `__tf*` extras (and their 22 references) are gone, and a full progress run
  stays 6,662/6,662. There never was vtable-specific masking: the data check masks every relocated word, and the
  typeinfo slot is simply no longer relocated.
  One codegen effect, in class_registry: without RTTI g++ 2.95 reuses a base's own vtable for a secondary base whose
  virtuals the class does not override (with RTTI the typeinfo slot made every secondary vtable distinct). The 12
  factories of the grab-spot classes (`X : SHAPE/XFM/VOL/TARGET/SO, GRABSPOT`) then stored `_vt$GRABSPOT` and
  scheduled their two vptr stores differently. The ELF shows the real rule: each of those classes overrides GRABSPOT
  slot 6 (delta != 0 in its secondary vtable) except CID36/CID37, which reuse CID35's (D_002D1EA8 for all three),
  as only a no-RTTI compiler does. The GRABSPOT view now lists its six slots and the ten classes declare the slot-6
  override (`VtF`); the 12 MATCH again and CID36/CID37 name CID35's secondary vtable (two link_aliases.txt lines
  fewer). Rule for views: a class with a secondary base must override at least one of that base's virtuals exactly
  when its secondary vtable in the ELF differs from the base's own.
- **Palettes D_0029A7C0/D_002A2900**: `__attribute__((section(".rodata")))` on the two definitions, with a comment.
  The original compiler placed a const object with a dynamic initializer zero-filled in `.rodata`, ours uses `.bss`;
  ee-gcc 2.95.3 accepts the attribute on the (non-const, written at startup) arrays without a warning, the
  assembler leaves the object's `.rodata` SHF_ALLOC only (the `"aw"` flag string gcc writes is ignored), the
  functions still MATCH and the data check reports both MATCH.
- **tn's zero `.rodata` SWCB** D_002A96E8 is not the same case: it is a null pointer-to-member constant `{0, 0, 0}`
  (its neighbour D_002A96F0 is a non-null one), statically zero, with no initializer writing it; it stays
  extern with the other PMF constants (literal phase). No other section attribute was added.

### Phase 3: address names

Goal: no `D_`/`func_` name that no object defines, so the link stops binding names to absolute
addresses (then tools/linkaliases.py; since integrate/round10 tools/link.py's `symbols()`) (an absolute address pins the data in place: no relocatable link, no mods, no port). Measured on all 932
objects tools/link.py builds: 917 address names (888 absolute, 29 aliases) before, 469 (467 absolute, 2 aliases)
after. Per-name classification and the remaining list: /home/claude/ref/reports/address_names/CLASSIFY.md.

Rules found:

- **Commons.** g++ 2.95 emits an uninitialized class static data member or template static data member as COMMON
  (`C` in nm), and C tentative definitions are commons; GNU ld allocates commons at the end of `.bss` (small ones in
  `.sbss`). That is why the splice pool words 0x2DD280.. / 0x4520xx are not in TU order. (The `.bss` from 0x4421A0
  to 0x452098, taken here for commons too, is in TU order: corrected in phase 7.) Defined as commons with the address name:
  `struct COMMONS_<tu> { static T c_X __asm__("D_X"); }; T COMMONS_<tu>::c_X;` at the end of one referencing TU (C:
  `T c_X[n] __asm__("D_X");`), sized by the gap to the next name; a common takes its type's alignment (int/char
  arrays 8, `qword` 16, `__attribute__((aligned))` is ignored), so 16-aligned starts with a 16-multiple size are
  `qword` arrays. matchtool checks COMMON placement and size. Open for a byte-matching real link: ld's common order
  is not the original's (the real names were template/class statics; their mangled names are not known). Superseded
  for the game's commons by phase 9: one file defines them all, in address order.
- **Interiors (b).** `#define D_X (*(T *)((char *)base_<OBJ> + 0xOFF))   /* field */` replaces each declaration
  (arrays: `(*(T (*)[N])(...))`, so `&D_X`, indexing and decay keep working), with `extern "C" char base_<OBJ>[]
  __asm__("<OBJ>");` after the first includes and an `#undef` where a namespace-local declaration's scope ends (a
  later declaration with another type must not leak). Comments name the SW field (offsets from sly2/sw.h). The SW
  type could replace the casts where a file has `SW` in scope (done for most of them in phase 4, below). Codegen: identical in 81 files; in two
  functions the base form changes code (CSE of the shared base in hud's func_00211298, offset folding in
  tu_201D78's UpdateReconTargetVisibility), so those three declarations stay extern.
- **Pointer records.** `namespace ANPTR_<tu> { void p_F() __asm__("F"); extern "C" char d_X[] __asm__("X");
  extern "C" { extern const unsigned int D_X[n] = {0xFFFF0000, (unsigned int)p_F}; } }` at the end of the TU: words as
  in the ELF, pointers through asm-labelled declarations, no existing declaration has to agree. A non-virtual PMF
  constant is 8 bytes {delta 0, index -1, pfn}; hud's widget records are {id, builder, arg, 0}. relverify checks the
  pointers (the data check masks them).
- **func_ labels and view inlines.** Labelling `func_00129658` as `__as__4CRefRC4CRef` in splicemap (and
  `func_00256CE8` as `__8VU_FLOATf` in tu_1553F0) makes g++ emit the file's own inline member with that mangled name
  (a referenced assembler name forces the deferred inline out): left as address names.
- **Prototype link.** Resolving through the defining objects exposes the prototype link's existing `.bss` placement
  differences (memcard, mpeg, sw, tn): `.text` from objects 1,281,279 equal bytes (68 fewer); relverify, which checks
  every relocation against the ELF, has 0 mismatches.

### Phase 5: data order

Goal: each object's `.bss`, `.data` and `.rodata` laid out as the ELF's, so a real link (no `-fdata-sections`,
`tools/link.py --tu-data`) puts every byte where the game has it. Measured with tools/link.py in both modes
(full-link.md, Status): config names at the wrong address 31 -> 0 (default mode) and 487 -> 349 (`--tu-data`: `.bss`
29 -> 0, `.sbss` 2 -> 0, `.rodata` 143 -> 46, `.data` 313 -> 303). Every touched file keeps all functions and data
symbols MATCH; no reorder changed codegen in its final form (one first attempt did, below).

**Emission order (g++ 2.95, checked on these objects).** It decides where each object lands inside its object's
section, and so in a link without `-fdata-sections`:

- **`.bss`.** An object with a constructor (an empty inline one counts) is emitted at its definition. Every other
  uninitialized object is emitted at the end of the file: first the global namespace's, in the order of their
  *first declaration* (a declaration in an included header counts: dli.h declares `D_002DD2FC`, so dl.cpp's
  `D_002DD2F8` came second), then each namespace's, the most recently opened namespace first (glob: `D_002DEB70` in
  `M_BeginRpProjVolume` came before `D_002DEB60`/`D_002DEB54` of the earlier `M_func_0016A000`), each in
  first-declaration order. Class and template static members are COMMON (phase 3) and go to the end of `.bss`/`.sbss`
  at link time. `-fdata-sections` does not split `.bss`, so this order matters in both link modes.
- **`.data`.** Initialized objects are emitted at their definition, in source order (namespaces do not matter).
- **`.rodata`.** A named constant is emitted at its definition; a function's string literals while the function is
  compiled (identical strings are shared within the TU), and its float constants and jump tables with it (the float
  constants after the jump tables). The decompiled sources name many of the original literals (`D_` strings,
  FLT_MAX words, PMF constants), so each named constant has to be defined between the functions where the ELF has
  it. Spelling, so that no function sees a definition (no folding, the declarations above stay as they are):
  `namespace RO_ORDER { extern const float r_D_002A5408 __asm__("D_002A5408") = 3.40282347e+38f; }` before the
  function the ELF puts after it, with a comment on the first one in each file; pointer records bring their
  asm-labelled pointee declarations into the same namespace.
- **Alignment the layout shows** goes on the definition (no header class changes): sprbuf's two uncached tag lists
  64 (0x3DD380 after D_003DD2C0 ends at 0x3DD360), g_joy 64 (0x2DFC00 after the words at 0x2DFBC0), prog's thread
  stack 16. Each is a choice that fits the layout (a 64-byte-aligned buffer and padding words would place the same);
  noted at the definition.

**Fixed.** `.bss`: dl (declaration before the include), gs (the libgraph double buffer's tail `D_002DEBD0` 0x1E0
bytes and the frame CRITSECT `D_002DFB40` defined; spelling `D_002DEBE0`/`D_002DECC0`/`D_002DECD0` as offsets into
the block made g++ share the base in RestoreGsBuffers/BlastAqwGifsBothFrames, so those three stay separate extern
address names), glob (definitions moved to file scope), shd (the 0x200-entry record table `D_003DA798` and the gap
word `D_003DD008` defined), prog (`D_002DD314` is a `.sbss` common), screen (the selected-job slot `D_003DA4D0` is a
0x20-byte record with an empty inline constructor: a plain pointer would be emitted after all nine screens), game
(g_game defined at file scope as `char[0x1C]`, `D_002DEB28` declared first), stepguard, joy, grab, sprbuf.
`.rodata` (in `--tu-data` mode now byte-identical to the ELF, relocated words aside): text, guardbhv, game,
stepguard, screen (with its `D_002C3268` string table and the three strings, which also closes the gap in its
`.data`), air, stepplayer, jt, prize, murray, sound, relay, tu_17F090, booty; hud from 84 to 9 differing bytes, hurt to 4 (its
shared literal).

**`-fdata-sections` (the default mode of tools/link.py).** It gives each named object its own section but leaves
every object's anonymous literals and jump tables in one `.rodata` section, so where the ELF interleaves named
constants with the functions' literals (most objects with both) that section cannot match in the default mode
whatever the source order: the 1,263 `.rodata` layout bytes of the default mode are this artifact and did not
change here. Decision (stylistic, keeps both measures): `-fdata-sections` stays in the default mode for now (it
isolates code from data-order problems: dropping it today would turn the default numbers into the `--tu-data` ones,
.rodata from objects 94.4% -> 88.6%), and `--tu-data` is the measure for data order. Once `--tu-data` is at least as
good, drop the flag (make `--tu-data` the default). (Done in phase 6: the flag is gone.)

### Phase 6: one link mode

Goal: the `--tu-data` layout at least as good as the `-fdata-sections` one, then one link mode. Done: tools/link.py
compiles without `-fdata-sections` (the `--tu-data` option and build/link/obj-tu are gone). Differing bytes 1,620
(old default) / 4,985 (old `--tu-data`) -> 115; config names at their address 7,401 / 7,401 (`--tu-data` had 349
wrong); `.data` and `.rodata` from objects byte-identical except 3 bytes (full-link.md, Status). 66 sources touched,
every function and data symbol MATCH, relocations of the touched objects 14,666 OK / 0 mismatched, no new
unresolved symbol, ld.lld 0 errors (no duplicate definitions). Scratch tools (not in the repo): plan2/mvdef (the
RO_ORDER moves), gather (one `.data` block), fixalign, dord/rplan/seccmp (layout against the ELF).

How the original got one copy where we emitted two (*shared literals*), by kind:

- **Float constants** (FLT_MAX, ...): g++ 2.95 keeps a constant pool per function, so a function that reads a const
  float whose definition it sees folds it into its own literal (bomb has three FLT_MAX words, one per function). The
  named constant is that function's literal: defined under its asm label just before the function (`RO_ORDER`),
  with the declaration kept, so the function loads the symbol (same `lui/lwc1`) and emits nothing of its own. Only
  valid where the constant is the first of the function's literals; true in all 30 cases here (po, blend, mark,
  path, bomb, tn, step, hurt, tu_171F58, tu_185130, ...).
- **Strings** are pooled per TU (`output_constant_def`): memcard's 14 and sw's 3 named strings were the functions'
  literals, so they are now spelled as literals where they are used and the definitions are gone (`(char *)` where
  a `void *` parameter takes one). The symbols stop existing; nothing else referenced them.
- **Aggregate constants** (pointer-to-member jobs) are pooled per TU like strings: memcard's UpdateSave and
  SetSaveState now spell the same `&MCJOB::GetInfo`, emitted once at 0x2A6BA0. The masked relocation had hidden a
  wrong target: SetSaveState's jobs were bound to `func_001AB0A0`/`func_001AB0F0` (no such functions); the ELF's
  words say McJobGetInfo and McJobGetDir.
- **Unreferenced literals** (strings no code in the ELF loads: a use the original compiled away): memcard
  0x2A6C80, cd's disc-type names 0x2A4F08-0x2A4FC0, defined under their address names where they sit. hud's
  0x2A8AE0 turned out to be the string a `char *` global (D_002C40A0) points at.

Other layout rules found:

- **The first part of `.rodata`** (up to about 0x2A3A00) holds named constants of many objects in TU order before
  every object's literals (cd's read modes and CRC table, the file-reference keys of tu_1A4E08, menu and mpeg, the
  two palettes). The reason the original compiler separated them is not known. Decision (stylistic, easy to rename):

### Phase 9: the commons file

User decision: the commons link.py still bound to absolute addresses are defined in one source file rather than
placed by a link.py ordering rule. The file is [src/game/app/commons.cpp](../../src/game/app/commons.cpp): app/
because it is the composition root (L11, docs/architecture.md), the one layer that may name splice's, core's,

allocated by ld), it has no functions, and tools/link.py lists it in `DATA_SOURCES` (it is in no config/matched.csv
row). Commons as absolute symbols: 69 -> 15.

How GNU ld allocated them, and how the file reproduces it:

- **The rule.** g++ 2.95 emits COMMON for an uninitialized class or template static data member (and for the
  `__sn...` sentry of a template static with a constructor) in every object that instantiates it; it does not for
  plain globals (those go to the object's `.bss`). GNU ld allocates commons after all input `.bss`: 8 bytes or less
  (its default `-G 8`) in `.sbss`, the rest at the end of `.bss`, in symbol hash-table order, which no placement of
  objects reproduces. In this ELF that is the whole `.sbss` (0x2DD280..0x2DD31C, 39 words: the game is built `-G0`,
  so only commons get there) and `.bss` 0x452098..0x452200 after collect2's.
- **The spelling.** Ordinary definitions, so the commons the other objects keep emitting resolve to them (a strong
  definition wins; link.py binds a common to an address only when no object defines it). `__attribute__((section
  (".sbss")))` / `(".bss"))` puts each in its block (a definition with a section name is never COMMON; `-G0` would
  put none in `.sbss`). g++ emits explicit instantiations of template statics after every other definition, which
  breaks the interleaving of block tables and pools in `.bss`; explicit specializations with a zero initializer
  (`template <> CPair *CGcObj<CPair>::s_aptPage[4] BSS = {0};`) are emitted in source order like the rest, and a
  zero initializer in a NOBITS section stays NOBITS. So: one `.sbss` and one `.bss` block, each in address order.
- **What is a proper member definition.** CGcObj<T>'s list words and block tables (sly2/gc.h) are template static
  data member definitions (explicit specializations, as above). The slot pools and splice heaps are not: a
  definition of `CSlotPool<>::s_pool` makes g++ generate its constructor call in this file (StaticInit code the
  ELF does not have; every TU's StaticInit constructs them through the sentries), so they are a SLOTHEAP under the
  mangled name, like the sentries (`int` under `__sn` + the mangled name) and prog's/hud's words (`D_002DD314`,
  `D_002DD318`: class statics of classes not known). dl's two words (g_psliFirst/g_pdliFirst, `D_002DD2F8`/`FC`)
  sit between the sentries in `.sbss`, so they were commons too; dl defined them as `.bss`, which split the block:
  they moved here (dl's line numbers kept).
- **Removed elsewhere**: the `COMMONS_<tu>` blocks of bif, frame, gc, splicemap, hud, sidebag, eval, ref, basic,
  spliceobj and prog (the phase 3 rule above is superseded for these), and dl's two definitions. Each object's code,
  data bytes and relocations are unchanged; every function and data symbol of the touched files MATCHes. config
  names the 11 sentries and the 11 pool/heap statics (symbol_addrs.txt, with sizes), so matchtool checks the

- **Not here**: the 15 commons of the SDK sources (989snd's buffers 0x443800..0x448500, libkernel's 0x44EF80). They

## Linkage of namespace-scoped declarations

A declaration inside a per-function namespace gets the namespace in its symbol unless it has C linkage or an asm
label; a file-scope declaration under a draft name or signature gets a symbol nobody defines. Relocations are masked,
so the match never shows a wrong callee or global symbol; a native link does. Rules (integrate/round2 and
link/round3, 2026-11-05; the data definitions of the Data section follow them too):

- A global (`D_...`, `g_...`) or a C-named function declared in a namespace: wrap the declaration in `extern "C" { }`
  inside the namespace (the name stays namespace-scoped for lookup, so the view's types still apply). If the same
  function is also declared `extern "C"` at file scope with identical parameter types, drop the namespace copy instead
  (the relay "ambiguous" row above).
- A callee declared under a view or Sly 1 name (`PosLoWorld`, `PvAllocSwImpl`, a view's `FRAME()`, `CRef(NODE *)`,
  `SPM::operator=`, a per-function `CRef::Decref()`): the jal target in the ELF names the real function; bind the
  declaration to it with an asm label, whether the target is a C name or a mangled C++ name
  (`qword PosLoWorld(LO *plo) __asm__("func_001A62E8");`, `FRAME() __asm__("STACKSCOPE_ctor");`,
  `void Decref() __asm__("Decref__4CRef");`). Works for free functions, constructors, members and operators, also
  inside an `extern "C" { }` block, and does not change code.
- File scope, target with a placeholder name (`func_`/`D_`): asm label; the source name stays (it is the better
  name: grep `__asm__("func_` for the candidates). Target with a real config name and the declaration is a free
  function or global: rename the identifier in the file to the config name, adding or dropping `extern "C"` to match
  the target's linkage (57 renames in round 3, e.g. `MakeSnd` -> `CreateSfxSound`, `InsertNodeBySlot` -> `AddXfAct`).
  Members, constructors, operators, declarations in shared headers (sly2/cref.h, cm.h, po.h, basic.h, lo.h,
  stepplayer.h, dmas.h) and config names that only disambiguate (`SetLoParent_1A58D0`,
  `strcpy1`): asm label. A header label is checked against every includer.
- Not for destructors: an asm label on a destructor declaration makes g++ 2.95 drop the destructor call (3 instructions
  per scope). Not for template members either: g++ 2.95 ignores an asm label on an explicit specialization
  (`template <> void CRefPtr<CMethod>::Attach(CMethod *) __asm__(...)` still references the mangled name).
- The symbol name can be codegen: `extern FR *g_pfrmOpen __asm__("D_002DEA4C")` (and the rename to `D_002DEA4C`)
  changes DrawSw's register allocation (8 instructions), like the path-hash quirk above. Such a declaration keeps its
  name; since data/vtables-2 config names 0x2DEA4C `g_pfrmOpen` and frm.cpp defines it so (frm still MATCHes).
- (Until data/vtables-2; the table is gone since, see "Vtables emitted (data/vtables)".) What source cannot bind went
  to config/link_aliases.txt, `symbol = target;` with the target recovered from the
  ELF: the vtables of namespace-scoped view classes (21 since types/views-2, act.cpp's curve classes and two local
  classes; class_registry's 191 went when its classes became real: their `_vt$<len><NAME>` are config data names
  now, see "Views unified (types/views-2)"), the view destructors (one left after types/views-1: brx_sw's
  `_$_3OBJ` = func_00184950), g_pfrmOpen, `__builtin_new` (the game's operator new,
  func_001AE4F8), three template members and `D_C0`. A file-scope destructor name can stand for different functions in
  different objects (`_$_3OBJ`; `_$_3SPM` was one until types/views-1), so such entries are per-object (`[source] symbol = target;`, for
  `objcopy --redefine-syms`). `python3 tools/linkaliases.py [objects...]` (retired in integrate/round10: link.py binds the
  address names itself) printed the table as linker-script lines
  (quoting names with `$`) and, given the objects, derived every `D_XXXXXXXX` / `func_XXXXXXXX` name that no object
  defines: the config name at that address when there is one (`func_002333B4 = memset;`), else the absolute address,
  which is only right in a link that keeps the original data image at its original addresses (docs/guides/full-link.md).
- Data definitions and the alias table: a definition inside a namespace carries `extern "C"` like a declaration
  (Data, "Namespace-mangled externs" and "Under C linkage in a namespace"). An alias target may be an object some file
  defines (`g_pfrmOpen = D_002DEA4C;`, frm's; 11 targets are defined objects or functions); an entry whose symbol
  becomes defined by an object must leave the table (none after data phase 2), and a `D_` name that becomes defined
  drops out of the address names linkaliases.py derived.
- Check the whole relocation, not only the symbol: for every relocation in a function or data object with a known
  address, the relocated field in the ELF (jal target, %hi/%lo pair, R_MIPS_32) minus the object's addend must be the
  address config gives the symbol. This found two source bugs the match masks (round 3): mpeg called
