# Merging a translation unit into one source file

Each leaf directory under `src/game/` is one original translation unit (TU) and today holds one file per function.
The merge wave turns `src/game/<subsystem...>/<tu>/` into one file `src/game/<subsystem...>/<tu>.cpp` whose functions
still match one by one. This page is the procedure, every mismatch cause met so far with the fix that worked, and the
list of merged TUs. Read it before merging a TU; add to it when you hit something new.

## Rules

- One file per TU, `<tu>.cpp` next to where the directory was. Functions in address order (the original source order).
  Use `.c` only if a function cannot match as C++, and say why in the file header (none so far).
- Commit per TU: `merge TU <name> (<n> functions) into <path>`, only when every function of the TU matches with
  `python3 tools/matchtool.py check <tu>.cpp`. The same commit updates `config/matched.csv` (`source` column of every
  function of the TU, nothing else), the subsystem `README.md` row, and doc links to the deleted files
  (`docs/reference/**`). If a TU does not fully match after a reasonable effort, do not merge it; record it below.
- Linker symbols do not change in a merge. A function whose current symbol is a plain name (`func_0011CCA8`,
  `PvAllocSlotheapClear`) is defined `extern "C"` in the `.cpp`; a function whose symbol is already mangled
  (`RenderGomerSelf__FP5GOMERP2CMP2RO`) is defined with the C++ signature that mangles to it. Renaming is
  tools/rename.py's job, not the merge's, so `config/symbol_addrs.txt` and `config/functions.csv` stay untouched.
  Declare callees with the linkage of their current definition (plain-named callees `extern "C"`); relocations are
  masked, so callee spelling never changes the match, but it keeps a later native link honest.
- Keep each function's `@sly2-annot` block above it. Drop the blocks of `StaticInit_<tu>` and its stub (they are
  generated now, see below).
- Types: a type used by more than one TU goes to `include/sly2/` (new headers or additions only; never change an
  existing layout; header changes in their own commits). TU-private types stay in the `.cpp`. Placeholder names from
  the per-function files (`W`, `O`, `S`) become the real class name where it is known (`CPair`, `CProc`, `MS`).
- Add layout asserts (`typedef char assert_X_size[sizeof(X) == N ? 1 : -1];`) for sizes the match or the data proves.

## Procedure

1. List the TU: rows of `config/matched.csv` whose `source` is in the directory, sorted by address. Some directories
   also hold an out-of-line inline/template instance from the linkonce area at the end of `.text` (0x254F00..);
   it belongs to the merged file too (see "Linkonce instances").
2. Draft: concatenate the files in address order. Drop `StaticInit_<tu>` and its 8-instruction stub, and start the
   file with:

   ```cpp
   // <tu>.cpp -- <what it is>. TU 0xSTART..0xEND (<n> functions, address order).
   // SLY2_ALIAS: __static_initialization_and_destruction_0=StaticInit_<tu>
   // SLY2_ALIAS: _GLOBAL_$I$*=<current name of the stub, e.g. func_0011CF40>
   #include "sly2/slotheap.h"
   ...other includes...

   // 0xADDR StaticInit_<tu> and its _GLOBAL_$I$ stub: generated by g++ for the six engine slot pools.
   SLY2_INSTANTIATE_SLOT_POOLS()
   ```

   Put `SLY2_INSTANTIATE_SLOT_POOLS()` directly after the includes (see "Pool order" for why).
3. Unify: one declaration per callee/global, shared types from `include/sly2/`, m2c bodies (`#include
   "m2c_prelude.h"`, `M2C_FIELD`) rewritten as readable C++ against those types. The m2c prelude is C only, so every
   m2c body in a merged TU has to be rewritten.
4. `python3 tools/matchtool.py check src/game/.../<tu>.cpp` until every function prints MATCH, and check that no
   function of the TU is missing from the object and no extra symbol with an address shows up.
5. `git rm -r` the directory, update matched.csv / README / doc links, commit.

A scratch helper that does steps 1, 2, 4 and 5 mechanically was used for this wave (not in the repo, by policy); it is
about 100 lines of Python around `tools/matchtool.py`'s `compile_src`, `obj_functions`, `apply_aliases` and `compare`.

### TUs with an older multi-function file (wave 3)

Five TU directories (heap, dmas, bis, vifs, gifs) held a hand-written multi-function `<tu>.cpp` from before the
restructure next to per-function files, some of which duplicated functions of that file; matched.csv then had two
rows for each duplicated function (one per source). What worked for all five:

1. Check the `@sly2-annot` blocks of the multi-function file for `TU <other>`: heap.cpp also held
   `Free__9CDynArray` and `Reserve__9CDynArrayi`, which lie inside TU dynarray. Move such functions into their own
   TU's merged file first, in a separate commit (and fix the doc links of those functions by hand afterwards: the
   finalize step rewrites every link to the old file, so they pointed at the wrong merged file for one commit).
2. Take the multi-function file as the base (its bodies are already C++ against the shared headers), split it at the
   annotation blocks and put the pieces in address order (none of the five was in order).
3. For a function defined in both places keep the copy that matches; when both match, keep the multi-function
   file's. Add the functions that only have per-function files, rewritten against the base file's types.
4. After finalizing, drop the duplicate matched.csv rows (same name, address and new source; keep the `match` row
   when the old non-matching copy left a row with a score).

Neither of the two "does not match inside the TU" cases was inline/class context (B6). vifs' `AddVifUnpack(UPK,
int, void *, int)` in vifs.cpp (0.279) was a different draft of the body (a count-down copy loop and a quad loop that
stored as it loaded); the per-function body, with its `UnpackHelper__4VIFS...` call written as a member call, matches
inside the TU. gifs' `AddPrimPack` in gifs.cpp (0.757) lacked the per-function copy's register pin
(`register QW *pqw __asm__("$3")`); the pinned body matches inside the TU.

## The generated static initializer (StaticInit_<tu> and _GLOBAL_$I$)

Almost every game TU ends with a 77-instruction `StaticInit_<tu>` (g++'s `__static_initialization_and_destruction_0`)
and an 8-instruction `_GLOBAL_$I$...` stub that calls it with `(1, 0xFFFF)`. They are not user code: g++ 2.95 emits
them for six template static slot pools that every TU instantiates, each guarded by a sentry
(`if (++sentry == 1) InitSlotheap(&pool, cb, c, 16)`). `include/sly2/slotheap.h` reproduces them with
`CSlotPool<CB, C>::s_pool` and the `SLY2_INSTANTIATE_SLOT_POOLS()` macro (from the cleanup pilot).

The object names of these two functions cannot be bound through `config/symbol_addrs.txt`:
`__static_initialization_and_destruction_0` is the same in every object, and the stub is named after the source file
(`_GLOBAL_$I$src_game_platform_memory_slotheap.cppQJeaaa`). The `// SLY2_ALIAS: obj=config` lines in the first 4000
bytes of the file rename them before comparison (matchtool and progress.py; a trailing `*` matches any suffix).
Alias them to the names config already has (`StaticInit_<tu>` and the stub's current name, usually `func_XXXXXXXX`).

TUs whose static initializer is not the standard 77 instructions have statics of their own. Read the target: if it
is the six pool blocks followed by more blocks of the same shape (`if (++sentry == 1) InitSlotheap(&obj, cb, c, 16)`),
the extra objects are template statics too. spliceutils (133 instructions) has five more slot heaps, 0x18 apart
(0x452188..0x4521E8); a TU-private `template <int CB, int C> struct CSpliceHeap { SLOTHEAP slotheap; ctor; static
CSpliceHeap s_heap; }` with five explicit instantiations after `SLY2_INSTANTIATE_SLOT_POOLS()` matched, and the code
that used the raw `D_004521xx` addresses now names `CSpliceHeap<CB, C>::s_heap`. Other shapes (`tu_1147D8` 185,
`tu_114AE0` 1926, sprbuf's SPRBUF array with a dynamic initializer) need their own spelling; not done in wave 1.

Wave 5 spelled the three of them as the file-scope objects they are, defined before `SLY2_INSTANTIATE_SLOT_POOLS()`
in their original order, so g++ generates the initializer:

- tu_1147D8 and tu_114AE0 contain no code of their own: `RGBA D_0029A7C0[16] = { RGBA(0, 0, 0, 0xF), ... };`
  (256 entries in tu_114AE0) with a private four-byte `RGBA` constructor, then `CLUT D_002DD500(D_0027A778);` and
  `BMP D_002DD520(D_0029A790);` whose inline constructors call func_001EAD98 / func_001EB050 (CopyClutHeader /
  CopyBmpHeader) on a header in .data. The natural array initializer matches; the per-function tu_114AE0 needed a
  dead countdown to steer cse, which g++'s own array-init code provides.
- sprbuf: `SPRBUF D_003DD2C0[2] = { MakeFirst(), MakeSecond() };` (SPRBUF's constructor memsets it), then the pools.
  With SLY2_ALIAS binding the initializer, the asm-label hack and its `SLY2_ASM: gnu-reorder-db` line go away and
  the merged file builds and matches with the default toolchain (all five functions); it no longer needs GNU as.
  Merged at the end of wave 5.

### Globals with destructors (wave 10)

A StaticInit whose `else` branch (initp == 0) calls destructors, and a third stub `_GLOBAL_$D$...` that calls it with
`(0, 0xFFFF)`, means the TU defines global objects with a constructor and a destructor. Five TUs had them: cm (g_cm),
sw (g_sw and a four-word table header), memcard (two dialog widgets), screen (nine screens) and sound (g_sndmgr).
What matched in all five: define each object in the merged file, in the original order and before
`SLY2_INSTANTIATE_SLOT_POOLS()`, as a view of its bytes whose inline constructor calls the C-named constructor and
whose inline destructor calls the linkonce destructor with g++'s in-charge flag (`~CMG() { func_00258290(this, 2); }`);
g++ then emits the destruction in reverse order itself. Add `// SLY2_ALIAS: _GLOBAL_$D$*=<stub>` next to the other two
aliases. Several objects of one shape: a small template over the size (screen's `SCRINL<CB>` / `SCRCTOR<CB>`); an
inline constructor taking a selector folds after inlining (memcard). When the destruction first releases member
pointers and then calls the base destructor (sound: three counted pointers, one an array of eight, then ~BASIC), make
the base destructor a base class's and the pointers members with inline destructors, and give the derived class an
explicit empty inline destructor (the implicit one was emitted out of line as `_$_7SNDMGRG` and called); g++'s own
array destruction is the `if (pa) { e = pa + 8; while (pa != e) Release(--e); }` loop of the target.

### Pool order

Naming a pool in code (for example a class-specific `operator delete` that frees into
`CSlotPool<0x18, 0x800>::s_pool`) instantiates that pool at that point. If the explicit instantiation comes later,
the pool's init block moves to the front of `StaticInit_<tu>`: varb showed a 4-instruction diff (two `li` pairs
swapped). Instantiating all six right after the includes keeps the order.

### The pools are real allocators

The pool objects at 0x4520A8 + 0x28*i are what Splice nodes are freed into: `CPair::operator delete` frees into pool
0 (`CSlotPool<0x14, 0x2000>`, slot size 0x14 == sizeof(CPair)) and `CVarb::operator delete` into pool 1
(`CSlotPool<0x18, 0x800>`, 0x18 == sizeof(CVarb)). Spell such uses as `&CSlotPool<CB, C>::s_pool.slotheap`, not as the
raw `D_004520A8`. Expected owners of the others (HYPOTHESIS): 0x28/0x200, 0x1C/0x800, 0xC/0xC8, 0x14/0x100 are
the other Splice node kinds (frames, procs, method records...).

Other observations:
- `.c` files compiled as C++ matched unchanged in every other case (about 20 files): expect B4 only for by-value
  structs that are passed on, and the `!`/bool difference above.
- Six linkonce helpers carried `// SLY2_CC:`/`// SLY2_CFLAGS: -O2 -G0` overrides in their own files; in the merged
  `.cpp` they match with the default C++ flags, so the overrides were not needed (spliceutils). Check this rather than
  copying overrides into a merged file (a file-level override would apply to every function of the TU).
- Per-function gcse stand-ins (brx_sw's dead `if (fNever)` block that sizes the gcse hash table) survive the merge:
  that table size is per function, not per file.

  in a follow-up commit of wave 1). Run `python3 -I tools/docs/linkcheck.py` after each merge.

## Path-hash quirk (asm functions)

GCC 2.95 hashes the source file name and the line number into the gcse ordering of inline-asm expressions; in rare
functions that ordering decides stack-slot numbering, so the match depends on (sum of path bytes, line) mod 287.
A merge changes both the path and the line of every function. If a merged function that contains inline asm misses
only by a few stack offsets, pin the name with `#line N "<repo-relative path>"` and keep the asm helper in the line
window that matches (example: func_001D3450 in `src/game/gameplay/objects/tu_1D1370.cpp`, namespace M_func_001D3450).

What wave 2 measured (on func_001D3450, by changing only its `#line 13 "<path>"` pin; MATCH unless noted):

| pin | result |
|---|---|
| original | MATCH |
| same path with two digits swapped (same byte sum) | MATCH |
| same path with one digit +5 (byte sum +5) | MATCH |
| line 23 (+10) | MATCH |
| line 53 (+40) | 64/637 instructions differ |
| `"a.cpp"`, line 13 | 5/637 differ |

So the input is (byte sum of the presumed file name, line of the asm text), with a window of roughly 30 lines; the
name that counts is the one `#line` sets, not the real file. The line is that of the asm statement itself, i.e. of the
inline helper that contains it (VU_FLOAT at line 57 there), not of the function that uses it.

Recipe for merging a sensitive function: directly before the asm helper's definition in the merged file write
`#line <line the helper had in the per-function file> "<per-function file's pinned path>"` (func_001D3450: `#line 57
"src/game/gameplay/objects/tu_1D1370/func_001D3450.cpp"` before `struct VU_FLOAT`), and directly after it
`#line <real next line> "<merged path>"` so diagnostics point at the merged file again. That reproduces (sum, line)
for the asm exactly, wherever the helper ends up in the merged file.
A cheaper equivalent is any (name, line) pair whose sum lands in the same window, but the verbatim pin is easier to
review. Helpers shared by several functions of the TU are defined once, so a sensitive function constrains where that
shared helper sits.

In practice it is rare: the three asm TUs of wave 2 (sjis: register-pinned `addu`/`sll` helpers; sky: a `pextuw`
helper; tu_1603B8: VU0 macro-mode asm with `"j"` operands) merged with no pin, and UpdateSky and ApplyXfmConstraint
still matched under eight different `#line` pins each. Only functions where gcse PRE creates pseudos from an asm (and
those pseudos then get stack slots) are sensitive. tu_1D1370 (44 functions), which holds the one known case, was
merged in wave 9: its namespace keeps the per-function file's verbatim `#line 13 "src/game/gameplay/objects/tu_1D1370/
func_001D3450.cpp"` (the string only names the presumed file; the directory is gone) and a `#line <next line>
"src/game/gameplay/objects/tu_1D1370.cpp"` after the namespace restores the merged name. func_001D3450 and every
function after it matched.

Wave 5 merged 20 more asm TUs (VU0 macro-mode, VU0 microprogram calls, EE 128-bit asm, register pins, allocation-only
operands) and none needed a pin: every miss was a C-vs-C++ or declaration difference (mismatch table). That includes
the functions whose per-file notes describe stack-slot-sensitive spellings (LaunchSoFromLauncher in tu_1D6848,

## Linkonce instances

Some TU directories also hold a small function from the linkonce area (0x254F00..0x259DE4): an out-of-line copy of an
inline member or template, homed in the TU that first uses it (proc 0x257038, varb 0x257430: a counted-pointer store).
Keep it in the merged file, after the TU's own functions, as a plain C-linkage function under its current symbol,
with a comment. Turning it back into the inline member it was would also need the callers to stop inlining it, which
is a separate step. For linkonce copies that no code calls, see the next section.

## Inline functions and linkonce copies

(Inline pass 1.) A function defined in a header (inline, in-class member, template) is compiled into every TU that
needs an out-of-line copy of it, in its own section `.gnu.linkonce.t.<symbol>` with a weak symbol; the linker keeps one
copy and puts it in the linkonce area 0x254F00..0x259DE4. So the way to "home" such a copy is to define the function in
its header and make one TU need it. tools/matchtool.py and tools/progress.py find it there with no change: they compare
every FUNC symbol of the object by name (weak and linkonce ones included; each symbol is read from its own section).

What makes g++ 2.95 emit the copy (all measured with matchtool on a scratch file):

- Taking its address in any TU (or a call that is not inlined) emits a free inline function, and an inline member of a
  class without virtual functions, in that TU.
- An inline member of a polymorphic class is NOT emitted there: the TU only references it as an undefined symbol.
  g++ emits the inline members of such a class only in the class's key TU (the one that defines its first non-inline
  virtual function, where the vtable goes; compare bq's key-TU extras above), and only those that TU needs. No TU of
  ours defines LO's, SO's, STEPPLAYER's... key function, so the member form cannot produce the copy.
- Unused inline functions in a header emit nothing: after the pilot all 163 sources that include `sly2/` headers
  were rebuilt; every function still matched and no addressed symbol appeared in another object.

The 56 functions that were in src/game/core/linkonce/unhomed (removed in pass 3) were all of one kind: no code refers to them; the only references
are pointers to member functions (`{0xFFFF0000, pfn}`: delta 0, index -1, non-virtual) in the option table g_aeopid
(D_002AC880, 0x28-byte EOPID records: get PMF at +0x8, set at +0x10, setUser at +0x18, ensure at +0x20). The owner class
of a record is the root-most class whose option array in g_mpcidarysplopt (D_00279AD0, 199 x {count, SPLOPT *}) lists
it. g_aeopid lives in crt0_splicewrap's .data and is not in the source, so:

- the accessor becomes an inline function in its class's header (sly2/cm.h, lo.h, so.h, xfm.h, stepplayer.h,
  guard.h; function templates in emitter.h, pass 3), written against the header types;
- src/game/app/eopid_linkonce.cpp includes the headers and takes the addresses as g_aeopid does, one
  `SLY2_EOPID_REF(addr, &func)` line each (`__typeof__(pfn) g_eopidref_<addr> = pfn;`: data, ignored by the tools).
  It is in app/ because it includes headers of every layer, as crt0_splicewrap does; matched.csv names it as the
  source of those functions, and the doc links point at the header that defines each one;
- the symbol becomes the function's real mangled form with tools/rename.py (run it BEFORE writing the header
  definitions: it sweeps the placeholder token in include/ too, and turned the first header members into
  `func_X__2CM()` declarations).

Free functions, not members: the setters stored in the same records are free functions taking the object first
(SetCmPos, SetStepplayerHp), so the getters stored next to them as PMFs can be free functions too, and a member of a
polymorphic class could not have been emitted by the table's TU in the original either (above). The first pilot
commit (82fdbfe5) used members (`func_X__2CM`), the next one renamed them to `func_X__FP2CM`. Names stay placeholders
(`func_<addr>` with the parameter types the mangled name needs); the comment next to each says what it reads.

They stay free inline functions for now (house style, as Sly 1's free-function convention: `SetCmPos(CM *, ...)`, not
`CM::SetPos`). Revisit them as members once the key source files of their classes (the TU that defines each class's
first non-inline virtual function, where g++ emits the vtable and the inline members) are merged: only there can a
member form produce the linkonce copy, so the question can be settled by a match rather than by taste.

## Data

`matchtool.py check` also verifies every data symbol a file DEFINES whose address is known (a `D_XXXXXXXX` name, or a
`name = 0xADDR; // type:data size:0xN` line in config/symbol_addrs.txt): initialized data byte for byte against the
ELF with relocated words masked, .bss by placement (and size, when symbol_addrs.txt gives one). It prints one line per
data symbol after the functions: `D_002C0D00 @0x2C0D00 [.data 0x4]: MATCH`, or the differing words
(`!! <addr>  <target bytes> | <ours>`), or a placement problem (`ours is zero-initialized (bss), target is in .rodata`).
Extern declarations are not checked; a symbol with no known address (template statics, `g_eopidref_*`) is skipped.

Defining a TU's data (pilot, 2026-11-04: pipe, water, hnd, sensor, memory):

1. Find what the TU owns: the survey (/home/claude/ref/reports/data_survey/globals.csv, columns `owner_guess`,
   `owner_confidence`) lists every D_ with its section, estimated size and users. Data is linked in TU order like
   code, so the TU's .data/.bss is the range between the previous and the next TU's data; a word inside that range
   that no code names (pipe's D_002C0D04) is the TU's too.
2. Replace the TU's `extern` declarations by definitions with the values read from the ELF, in address order (g++
   emits .data and .bss in definition order; memory's object reproduced the target's .bss offsets exactly). Use the
   type the code reads and the layout shows: a 16-byte stride of three floats is a CLQ (water), the gap to the next
   TU's data sizes an array (memory's `D_002F63A0[50]`). Keep the constness the section shows (.data = non-const;
   .rodata = const or a literal). Do not claim padding-looking zeros up to the next TU's data (hnd, sensor).
3. Leave `extern` declarations in other TUs' files as they are (memcard still declares memory's globals).
4. `python3 tools/matchtool.py check <tu>.cpp`: every function still MATCH (defining a global in the TU that uses it
   can change code generation) and every data symbol MATCH. Commit per TU: `data: define <tu>'s ... in <tu>.cpp`;
   config/matched.csv does not change.

Known limits: the ELF has no symbol table, so a definition that is too short passes unless symbol_addrs.txt gives
`size:`; relocated words are masked, so a wrong pointer in a table still passes; unnamed literals and strings are not
checked (only named symbols). Our compiler puts a const object with a dynamic initializer in .bss, where the original
has it zero-filled in .rodata: tu_1147D8's and tu_114AE0's palettes `D_0029A7C0` / `D_002A2900` report that placement
difference (their functions match). The vtables are linkonce data at the end of .data (0x2C8940..0x2DD230), not owned
by any TU, and the end of .bss from about 0x4421A0 is not in TU order (hud, frm, memcard, mpeg, thread mixed, likely
common symbols): do not define data there by layout.

## Linkage of namespace-scoped declarations

A declaration inside a per-function namespace gets the namespace in its symbol unless it has C linkage or an asm
label. Relocations are masked, so the match never shows a wrong callee or global symbol; a native link does. Rules
(integrate/round2, 2026-11-05):

- A global (`D_...`, `g_...`) or a C-named function declared in a namespace: wrap the declaration in `extern "C" { }`
  inside the namespace (the name stays namespace-scoped for lookup, so the view's types still apply). If the same
  function is also declared `extern "C"` at file scope with identical parameter types, drop the namespace copy instead
  (the relay "ambiguous" row above).
- A callee declared under a view or Sly 1 name (`PosLoWorld`, `PvAllocSwImpl`, a view's `FRAME()`, `CRef(NODE *)`,
  `SPM::operator=`): the jal target in the ELF names the real function; bind the declaration to it with an asm label
  (`qword PosLoWorld(LO *plo) __asm__("func_001A62E8");`, `FRAME() __asm__("STACKSCOPE_ctor");`). This works for free
  functions, constructors and members, and does not change code.
- Not for destructors: an asm label on a destructor declaration makes g++ 2.95 drop the destructor call (3 instructions
  per scope). The 41 view destructors that stand for `STACKSCOPE_ctor_1AE4A0(this, 2)` and `PairPtr_Release` stay
  namespace-mangled; a native link needs a linker-script alias for them, or the shared class in a header.
- Still open (C++-named targets, out of this pass): members, constructors and free functions of namespace views whose
  real symbol is mangled (`Decref__4CRef`, `__4CRefRC4CRef`, `AddDmaCnt__4DMAS`, 227 references), the vtables of
  namespaced view classes (`_vt$Q23REG...`, 214, mostly class_registry's construction views) and 600-odd file-scope
  declarations whose name or signature differs from the config symbol. The full list with the recovered targets is in
  the integration report (LINKCHECK.md, not in the repo).

## class_registry

src/game/app/class_registry/ (424 functions, the non-generated part of the crt0_splicewrap block, not a TU of its
own) is one file, src/game/app/class_registry.cpp, in address order: the two crt0 asm fragments, the 33 Splice
option thunks, the 185 `New<Class>` factories, the 199 `Get<Class>ClassDesc` getters, the generated static
initializer, and the out-of-line constructors STEPGUARD_ctor, JT_ctor and MURRAY_ctor from the linkonce area. All
424 match. What it needed:

- Factories are `return new CLASS;` over construction views in `namespace REG`: one struct per class with the real
  name, parent and size (class-tree.md; cb asserted), and only what construction shows. Each view declares
  `virtual CLASSINFO *Pclassinfo();` (the slot-6 override every class has), so each class gets its own vtable and
  stores its vptr; intermediate vptr stores disappear unless a call separates them, as in the game. g++ 2.95 order:
  base constructors, vptr, member constructors, body.
- An asm label on a constructor declaration binds an out-of-line constructor to its current symbol
  (`STEPGUARD() __asm__("STEPGUARD_ctor");`), for calls and for the definition alike.
- BASIC's two words must be members with clearing constructors (`PTR<T>`, CRefPtr's shape), not stores in BASIC's
  constructor body: STEPGUARD_ctor's embedded CID146 was 5/33 off otherwise (the +0x4 clear addressed from the member,
  not from the enclosing object). The ten grab-spot classes take a second base GRABSPOT (0x20 data bytes, then its
  vptr).
- An asm label that equals the mangled name of an inline function of the file makes g++ emit that inline function
  under it: GLOBSET's constructor (0x167310, current symbol `__4CRef`) labelled `"__4CRef"` added a weak copy of the
  thunks' CRef::CRef() as an extra `__4CRef`. The label `"__4CRef "` (trailing space, dropped by the assembler) avoids
  it; renaming 0x167310 would remove the need.
- The shared class headers (sly2/lo.h, so.h, ...) cannot construct as the game does (sly2/basic.h's `CRefPtr()` does
  not clear, GLOBSET has no constructor), hence the separate namespace.
