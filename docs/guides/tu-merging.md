# Merging a translation unit into one source file

Each leaf directory under `src/game/` is one original translation unit (TU) and today holds one file per function.
The merge wave turns `src/game/<subsystem...>/<tu>/` into one file `src/game/<subsystem...>/<tu>.cpp` whose functions
still match one by one. This page is the procedure, every mismatch cause met so far with the fix that worked, and the
list of merged TUs. Read it before merging a TU; add to it when you hit something new.

## Rules

- One file per TU, `<tu>.cpp` next to where the directory was. Functions in address order (the original source order).
  Use `.c` only if a function cannot match as C++, and say why in the file header (none so far).
- Commit per TU: `merge TU <name> (<n> functions) into <path>`, only when every function of the TU matches with
  `python3 tools/matchtool.py check <tu>.cpp`. The same commit updates `config/matched.csv` (`source` column of every
  function of the TU, nothing else), the subsystem `README.md` row, and doc links to the deleted files
  (`docs/reference/**`). If a TU does not fully match after a reasonable effort, do not merge it; record it below.
- Linker symbols do not change in a merge. A function whose current symbol is a plain name (`func_0011CCA8`,
  `PvAllocSlotheapClear`) is defined `extern "C"` in the `.cpp`; a function whose symbol is already mangled
  (`RenderGomerSelf__FP5GOMERP2CMP2RO`) is defined with the C++ signature that mangles to it. Renaming is
  tools/rename.py's job, not the merge's, so `config/symbol_addrs.txt` and `config/functions.csv` stay untouched.
  Declare callees with the linkage of their current definition (plain-named callees `extern "C"`); relocations are
  masked, so callee spelling never changes the match, but it keeps a later native link honest.
- Keep each function's `@sly2-annot` block above it. Drop the blocks of `StaticInit_<tu>` and its stub (they are
  generated now, see below).
- Types: a type used by more than one TU goes to `include/sly2/` (new headers or additions only; never change an
  existing layout; header changes in their own commits). TU-private types stay in the `.cpp`. Placeholder names from
  the per-function files (`W`, `O`, `S`) become the real class name where it is known (`CPair`, `CProc`, `MS`).
- Add layout asserts (`typedef char assert_X_size[sizeof(X) == N ? 1 : -1];`) for sizes the match or the data proves.

## Procedure

1. List the TU: rows of `config/matched.csv` whose `source` is in the directory, sorted by address. Some directories
   also hold an out-of-line inline/template instance from the linkonce area at the end of `.text` (0x254F00..);
   it belongs to the merged file too (see "Linkonce instances").
2. Draft: concatenate the files in address order. Drop `StaticInit_<tu>` and its 8-instruction stub, and start the
   file with:

   ```cpp
   // <tu>.cpp -- <what it is>. TU 0xSTART..0xEND (<n> functions, address order).
   // SLY2_ALIAS: __static_initialization_and_destruction_0=StaticInit_<tu>
   // SLY2_ALIAS: _GLOBAL_$I$*=<current name of the stub, e.g. func_0011CF40>
   #include "sly2/slotheap.h"
   ...other includes...

   // 0xADDR StaticInit_<tu> and its _GLOBAL_$I$ stub: generated by g++ for the six engine slot pools.
   SLY2_INSTANTIATE_SLOT_POOLS()
   ```

   Put `SLY2_INSTANTIATE_SLOT_POOLS()` directly after the includes (see "Pool order" for why).
3. Unify: one declaration per callee/global, shared types from `include/sly2/`, m2c bodies (`#include
   "m2c_prelude.h"`, `M2C_FIELD`) rewritten as readable C++ against those types. The m2c prelude is C only, so every
   m2c body in a merged TU has to be rewritten.
4. `python3 tools/matchtool.py check src/game/.../<tu>.cpp` until every function prints MATCH, and check that no
   function of the TU is missing from the object and no extra symbol with an address shows up.
5. `git rm -r` the directory, update matched.csv / README / doc links, commit.

A scratch helper that does steps 1, 2, 4 and 5 mechanically was used for this wave (not in the repo, by policy); it is
about 100 lines of Python around `tools/matchtool.py`'s `compile_src`, `obj_functions`, `apply_aliases` and `compare`.

## The generated static initializer (StaticInit_<tu> and _GLOBAL_$I$)

Almost every game TU ends with a 77-instruction `StaticInit_<tu>` (g++'s `__static_initialization_and_destruction_0`)
and an 8-instruction `_GLOBAL_$I$...` stub that calls it with `(1, 0xFFFF)`. They are not user code: g++ 2.95 emits
them for six template static slot pools that every TU instantiates, each guarded by a sentry
(`if (++sentry == 1) InitSlotheap(&pool, cb, c, 16)`). `include/sly2/slotheap.h` reproduces them with
`CSlotPool<CB, C>::s_pool` and the `SLY2_INSTANTIATE_SLOT_POOLS()` macro (from the cleanup pilot).

The object names of these two functions cannot be bound through `config/symbol_addrs.txt`:
`__static_initialization_and_destruction_0` is the same in every object, and the stub is named after the source file
(`_GLOBAL_$I$src_game_platform_memory_slotheap.cppQJeaaa`). The `// SLY2_ALIAS: obj=config` lines in the first 4000
bytes of the file rename them before comparison (matchtool and progress.py; a trailing `*` matches any suffix).
Alias them to the names config already has (`StaticInit_<tu>` and the stub's current name, usually `func_XXXXXXXX`).

TUs whose static initializer is not the standard 77 instructions have statics of their own. Read the target: if it
is the six pool blocks followed by more blocks of the same shape (`if (++sentry == 1) InitSlotheap(&obj, cb, c, 16)`),
the extra objects are template statics too. spliceutils (133 instructions) has five more slot heaps, 0x18 apart
(0x452188..0x4521E8); a TU-private `template <int CB, int C> struct CSpliceHeap { SLOTHEAP slotheap; ctor; static
CSpliceHeap s_heap; }` with five explicit instantiations after `SLY2_INSTANTIATE_SLOT_POOLS()` matched, and the code
that used the raw `D_004521xx` addresses now names `CSpliceHeap<CB, C>::s_heap`. Other shapes (`tu_1147D8` 185,
`tu_114AE0` 1926, sprbuf's SPRBUF array with a dynamic initializer) need their own spelling; not done in wave 1.

### Pool order

Naming a pool in code (for example a class-specific `operator delete` that frees into
`CSlotPool<0x18, 0x800>::s_pool`) instantiates that pool at that point. If the explicit instantiation comes later,
the pool's init block moves to the front of `StaticInit_<tu>`: varb showed a 4-instruction diff (two `li` pairs
swapped). Instantiating all six right after the includes keeps the order.

### The pools are real allocators

The pool objects at 0x4520A8 + 0x28*i are what Splice nodes are freed into: `CPair::operator delete` frees into pool
0 (`CSlotPool<0x14, 0x2000>`, slot size 0x14 == sizeof(CPair)) and `CVarb::operator delete` into pool 1
(`CSlotPool<0x18, 0x800>`, 0x18 == sizeof(CVarb)). Spell such uses as `&CSlotPool<CB, C>::s_pool.slotheap`, not as the
raw `D_004520A8`. Expected owners of the others (HYPOTHESIS): 0x28/0x200, 0x1C/0x800, 0xC/0xC8, 0x14/0x100 are
the other Splice node kinds (frames, procs, method records...).

## Mismatch causes and fixes

| symptom | cause | fix | seen in |
|---|---|---|---|
| a function from the directory is missing from the object, or shows up under a mangled name | the per-function `.c` file had C linkage; in a `.cpp` the name is mangled | `extern "C"` on the definition (or in a prototype block before it) | every TU with `.c` files |
| `StaticInit_<tu>`/stub `not in object` / `no address known` | missing SLY2_ALIAS lines, or the stub alias names a symbol config does not have | alias to the names in config/functions.csv | — |
| 4 instructions differ in StaticInit (two `li a1`/`li a2` pairs swapped) | a pool named in code before the explicit instantiation | `SLY2_INSTANTIATE_SLOT_POOLS()` right after the includes | varb |
| a caller is ~40 instructions short around a `delete` | the per-function file had a class-specific `operator delete` that a hand-filtered draft lost | concatenate the files verbatim first; never filter lines when drafting | pair (drafting mistake) |
| field access through a raw offset (`*(ulong *)((char *)p + 0x148) &= ~(1UL << 35)`) | — | the header bitfield (`SO::fUnk35`) gives the same `ld/and/sd` | ms |
| a `.c` body is 2-3 instructions off as C++ around a bit test: target `andi 1; bnez`, ours `xori 1; andi 1; beqz` | in C++ `!` yields `bool`, so `!(x & 1)` is computed, not branched on | write `(x & 1) == 0` | tu_15DC80 (func_0015E1D8) |
| a `.c` function that passes an 8-byte struct by value differs: target spills the incoming `a2` (`sd a2,0(sp)`) and reloads it for the call (`ld a2,0(sp)`); ours copies it through a stack temporary with `ldl/ldr/sdl/sdr` and has a bigger frame | g++ 2.95 copies every by-value class argument into a temporary (pilot blocker B4) | not solved. Tried: an `aligned(8)` copy of the type for the parameter (keeps it in a register: 39/40 differ); punning the parameter as `long` (30/39 differ). Leave the TU unmerged | callback (EnsureSwCallback; PostSwCallback and ClearSwCallbacks, which only receive the struct, match as C++) |
| shared-base stores (`lui; addiu; sw 0/4/8/C(base)`) where the target has one `lui` per store | the target's four words are separate globals, not one struct | keep separate `extern int D_...` declarations | spliceutils (GcShutdown*Pool) |
| compile error: conflicting declarations of the same `extern "C"` function | two `.c` files declared one callee with different parameter types (C allowed it) | one prototype with the real types; callers cast if needed | tu_19F0A8 (SetStepguardSpecial), brx_sw (CBinaryInputStream readers) |
| compile error: `redefinition of struct RGBA` (or CLOCK, DL...) | a TU-private type collides with a shared header | include only what the TU uses (slotheap.h deliberately does not include basic.h); a private type whose inline members shape codegen (tu_15DC80's `RGBA() {}`) stays private, under its own name if the TU also needs the shared header (brx_sw renamed its POD copy `RGBAPOD`) | brx_sw, tu_15DC80 |
| an m2c body calls `UpdateLo()` / `UpdateStepguard()` with no arguments | m2c could not see that `a0`/`f12` are passed through unchanged | give the function the real parameters and pass them on (`UpdateStepguard(pguard, dt)`); no instructions change | tu_14FAC8, tu_15DC80 |

Other observations:
- `.c` files compiled as C++ matched unchanged in every other case (about 20 files): expect B4 only for by-value
  structs that are passed on, and the `!`/bool difference above.
- Six linkonce helpers carried `// SLY2_CC:`/`// SLY2_CFLAGS: -O2 -G0` overrides in their own files; in the merged
  `.cpp` they match with the default C++ flags, so the overrides were not needed (spliceutils). Check this rather than
  copying overrides into a merged file (a file-level override would apply to every function of the TU).
- Per-function gcse stand-ins (brx_sw's dead `if (fNever)` block that sizes the gcse hash table) survive the merge:
  that table size is per function, not per file.
- When rewriting doc links, match `\.(cpp|c)` in that order: `(c|cpp)` stops at `.c` and leaves `pp` behind (fixed
  in a follow-up commit of wave 1). Run `python3 -I tools/docs/linkcheck.py` after each merge.
- Not hit yet: inline methods or class definitions that become visible in the merged TU and change a function's
  codegen (pilot blocker B6, gifs/vifs), and the path-hash quirk below.

## Path-hash quirk (asm functions)

GCC 2.95 hashes the source file name and the line number into the gcse ordering of inline-asm expressions; in rare
functions that ordering decides stack-slot numbering, so the match depends on (sum of path bytes, line) mod 287.
A merge changes both the path and the line of every function. If a merged function that contains inline asm misses
only by a few stack offsets, pin the name with `#line N "<repo-relative path>"` and keep the asm helper in the line
window that matches (example: `src/game/gameplay/objects/tu_1D1370/func_001D3450.cpp`). None of the wave-1 TUs
contain asm, so it did not come up yet.

## Linkonce instances

Some TU directories also hold a small function from the linkonce area (0x254F00..0x259DE4): an out-of-line copy of an
inline member or template, homed in the TU that first uses it (proc 0x257038, varb 0x257430: a counted-pointer store).
Keep it in the merged file, after the TU's own functions, as a plain C-linkage function under its current symbol,
with a comment. Turning it back into the inline member it was would also need the callers to stop inlining it, which
is a separate step.
